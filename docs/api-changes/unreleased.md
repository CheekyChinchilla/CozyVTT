# API changes in Unreleased

What a program driving CozyVTT may notice in the next release. The HTTP routes and live-table events are not a versioned public API, but programs do drive them with a signed-in account. These are the changes such a program may notice; the changelog's entries explain each one for everyone else.

- *Live table: events.* A `token.move.end` refused because the sender may not move the token (`error` "You do not have permission to move this token" or "Spectators cannot move tokens") or may not act on its plane ("You cannot interact with spirit layer tokens") now always sends the sender, after the `error`, a `token.moved` with the token's stored position and `movedBy: null`, when the map fetch would give the sender that token. It used to be sent only when the same connection's `token.move.start` for the token had been accepted first; without one, the sender got only the `error`.
- *Live table: events.* One connection's `token.move.start` and `token.move.end` for the same token are now handled one after the other, in the order they arrive. The `token.move.start` a pick-up sends to others now always arrives before the `token.moved` of a drop sent right behind it, where the two could arrive the other way round, and a refused drop sent right behind its pick-up is now put back on the screens the pick-up reached. Events for different tokens do not wait for each other.
- *Live table: events.* `campaign.access.revoked` has a new `reason`, `not-member`, with the message "You are not a member of this campaign.". An `authenticate` naming a campaign the user is not a member of is answered with it; it was answered `error` "You are not a member of this campaign". One naming a campaign that does not exist is answered `campaign.access.revoked` with reason `campaign-deleted` and the message "This campaign does not exist. It may have been deleted."; it was answered `error` "Campaign not found". Either way `campaignId` is the campaign the `authenticate` named, the connection stays open, leaves every campaign room it was in (each of those campaigns gets `user.left` and `presence.state`) and is in no campaign, as after a removal. The other refusals of `authenticate` are still an `error`.
- *Live table: events.* A connection that asks to join a campaign within a minute of its user's removal or leave, or whose join finds the membership gone after it was first read, is sent `campaign.access.revoked` with the reason that removal or leave gave, `removed` ("You were removed from this campaign.") or `left` ("You left this campaign."). After the minute, or with no record of why, the reason is `not-member`. A join that found the membership gone on its second read always said `removed`. The minute is kept in the backend process's memory, so a restart forgets it.
- *Accounts and requests.* A user's `lastLoginAt` is now set when a sign-in completes: by `POST /api/auth/login` without two-factor authentication, `POST /api/auth/mfa/verify-login` with it, `POST /api/auth/register` when it signs the person in, and `POST /api/setup/init`. Registration and the setup wizard left it null, and `POST /api/auth/login` set it at the password step, including for a sign-in that then stopped at the code step or was refused with 403 `Account Pending Approval`. `POST /api/admin/users/:id/resend-invite` therefore answers 409 for an account that ran the setup wizard or registered and was signed in straight away (it answered 200), and 200 for an account whose only sign-in attempts were refused with 403 `Account Pending Approval` or stopped at the code step (it answered 409), since those no longer set `lastLoginAt`; and `POST /api/auth/reset-password` with an invitation link no longer restarts such an administrator's 7 days to set up two-factor authentication. `GET /api/auth/me` from a signed-in session sets a `lastLoginAt` that is still null, once, and the `user` it answers with carries the new value.
- *Accounts and requests.* The `RateLimit-*` headers on `POST /api/auth/mfa/verify-login` answers are now always the per-address limit's (5 wrong codes per 15 minutes from the address, `RateLimit-Policy: 5;w=900`), as on `POST /api/auth/login`. The per-account limit's replaced them, so `RateLimit-Remaining` counted the account's wrong codes from every address. The 429 `Too many MFA login attempts for this account, please try again later` keeps its `Retry-After`, and its `RateLimit-*` headers are now the address's.
- *Assets.* `DELETE /api/assets/:id` (with or without `force=true`) and `PATCH /api/assets/:id/scope` (a move out of the campaign) by a campaign asset's uploader who does not run the campaign now first read up to 100 of the campaign's other members' documents stored before 1.6.0 (a PDF among them, which names nothing) and not yet read for the assets they name. While any is still unread (more than 100 were waiting, another request is reading it, or its file could not be read), the delete answers 403 "Some older documents have not yet been checked for the pictures they show, so for now only the campaign's DM can delete this asset. Try again later." and the move 403 "Some older documents have not yet been checked for the pictures they show, so for now only the campaign's DM can move this asset out of the campaign. Try again later."; each request reads up to 100 more, newest first. A document whose file cannot be read is tried again by every request and keeps the refusal until it can be read; until then only the campaign's DM can delete or move the asset. A document read this way that shows the asset now gives the existing 403 "Others in the campaign use this asset, so only the campaign's DM can delete it" (the move: "Others in the campaign use this asset, so only the campaign's DM can move it out of the campaign"); before, until the document had been read, the delete answered 200 with `force=true` and 200 or 409 `ASSET_IN_USE` without it, and the move answered 200. The campaign's DM and admins are answered as before.
- *Character data.* `GET /api/characters/templates/PATHFINDER_2E/blank` now answers with no `classDC` in `data`; it carried `{ "total": 10, "keyAttribute": "strength", "proficiencyRank": "untrained" }`. A Pathfinder 2e character made from the blank sheet therefore has no `classDC` until the editor saves one, which it does once a key attribute is chosen; it no longer adds one with `keyAttribute` `intelligence` to a sheet that has none. `classDC` was already optional, and stored sheets are unchanged.
- *Creatures.* A stat block whose own `gameSystem` is `CALL_OF_CTHULHU_7E` now takes each of the six `abilities` as a whole number from 0 to 9,999, and each `skills` value as a whole number from -50 to 999. It took 0 to 30 and -50 to 50, and answered 400 past them with "Too big: expected number to be <=30" (or `<=50`) at `abilities.<score>` or `skills.<name>`; past the new bounds the message ends `<=9999` or `<=999`. This holds wherever a stat block is taken: `POST /api/campaigns/:campaignId/creatures` and `PUT .../creatures/:creatureId`, the token template routes, `POST /api/campaigns/:campaignId/maps/:id/tokens`, `PUT .../tokens/:tokenId` and a campaign import. Every other stat block, one with no `gameSystem` among them, keeps 0 to 30 and -50 to 50 with the same messages, and `savingThrows` keeps -50 to 50 in every system. A stat block that breaks several rules now lists its score and skill messages after the others, so a token's refusal, which names only the first, may name a different rule. The web client now sets a stat block's `gameSystem` to the campaign's whenever a creature's, token's or token template's stat block is edited.
- *Accounts and requests.* `PUT /api/users/:id` now caps changing your own email address at 5 attempts an hour per account, from every sign-in and address. Every request that would change your own address counts: with the right `currentPassword`, a wrong one or none, to an address another account has (still answered 400 "Email already in use") or a free one, and one that makes the change. Past the cap it answers 429 `{ "error": "Rate Limited", "message": "You have tried to change your email address 5 times in the last hour, the most this server allows. Please try again later." }` with `Retry-After` (seconds until the oldest counted attempt is an hour old) and no `RateLimit-*` headers of its own, before the password is checked; the refusal is not counted. A request that changes only the display name, avatar or bio, or sends the current address in any letter case, does not count and is not held, and an admin changing someone else's address is not capped.
- *Walls and lights.* New route `POST /api/campaigns/:campaignId/maps/:id/walls/batch`, DM only (403 for a player, a spectator or anyone outside the campaign, 401 signed out, 404 for a map not in the campaign or deleted before the write), adds many wall segments in one request. Body `{ "segments": [...] }`, each segment as `POST .../walls` takes it (`id` optional and generated when missing). It answers 400 `Validation Error`, changing nothing, when `segments` is not a list ("segments must be a list of wall segments"), holds more than 5000 ("Maximum 5000 wall segments per map") or holds an invalid segment (the schema's message after "Wall <index>: ", counting from 0). Otherwise each segment is judged in order under one lock, as `POST .../walls` would judge it alone, counting the segments added before it in the request, and skipped when it reaches more than 500 grid squares outside the map ("A wall reaches too far outside the map. Walls can extend up to 500 squares past its edges."), the map holds 5000 ("Maximum 5000 wall segments per map") or its `id` is on the map or was added earlier in the request ("A wall segment with that id is already on this map"). The answer is always 200 `{ "added": [segments added, with ids], "skipped": [{ "index", "reason" }], "total": walls on the map now }`, nothing added included. One `walls:replaced` with the map's whole list goes to the map's readers when any segment was added, followed on a lit current map by `map.changed` for each player; nothing is sent when none was. The web client's Mapmaker Save now sends a room's walls this way, once, where it sent one `POST .../walls` per wall and stopped at the first refusal.
- *Character data.* A `DND_5E` sheet takes a new optional field in `data`, `initiativeAdvantage`, true or false, in `POST /api/characters`, `PUT /api/characters/:id`, `POST /api/character-templates` and `PUT /api/character-templates/:id`. It was dropped from the stored sheet before; a value that is not true or false is now answered 400 "Character data does not match game system schema" (for a template, "Template data does not match game system schema"), with `validationErrors` naming the path `initiativeAdvantage`. `GET /api/characters/templates/DND_5E/blank` now carries it as `false`. With it `true`, an `initiative.roll` for a token bound to that character rolls `2d20kh1` plus the modifier, where it rolled `1d20` plus the modifier: the `expression` of the `dice.rolled` it sends, and of the roll stored in the dice history, reads like `2d20kh1+2`, and its `breakdown` holds two d20 results with the higher one kept. A sheet with it `true` whose `exhaustionLevel` is 1 or more, or whose `conditions` hold `poisoned`, still rolls `1d20` plus the modifier, as does a sheet without it or with it `false`.
- *Campaign archives.* `POST /api/campaigns/import/preview`, `POST /api/campaigns/import` and `POST /api/admin/backups/restore` read an uploaded archive's directory with another reader. It finds the end-of-directory record wherever a record with a comment of up to 65,535 bytes can start, where the old one looked only in the archive's last 80 bytes, and it requires that record and its comment to end the file. Every archive a CozyVTT version wrote is answered as before, and the entry-count limits are unchanged; the count they check is now always the one the reader goes on to read. Archives no CozyVTT version writes may be answered differently. One whose own comment is longer than 58 bytes is now read, and so is one whose end-of-directory record lists exactly 65,535 entries with no ZIP64 record after them; each was answered 400 "The file is not a ZIP archive, or it is damaged.". These are now answered 400 "The file is not a ZIP archive, or it is damaged." (on a restore with " Nothing was changed." after it) before any entry is unpacked, where they were read: one with bytes after its end-of-directory record and that record's comment; one whose end-of-directory record names a disk other than the first; one whose directory has a record with the wrong signature; one with an extra field whose declared length runs past the record's extra area; one with a record that marks a size or offset 0xFFFFFFFF whose ZIP64 extra field does not carry it; and one with an entry flagged for strong encryption (general purpose bit 6). A restore of the last answered 400 "<name> is encrypted, which an archive from this server never is. Nothing was changed." when bit 0 was set too, and an import did the same when it read that entry. A ZIP64 locator in front of an end-of-directory record whose fields are not full is now always followed: the entry count and directory offset are taken from the ZIP64 record it points to, and the archive is refused as above when that record is bad, or with the entry-count message when its count is over the limit. The old reader used the short record's fields there, so an archive whose ZIP64 record claims 1,000,000 entries and whose short record says 1 is now refused with "The archive lists 1,000,000 files, more than the 1,000 it may hold." on an import, where 1.6.0 read one entry.
