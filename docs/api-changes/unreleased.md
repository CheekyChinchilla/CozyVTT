# API changes in Unreleased

What a program driving CozyVTT may notice in the next release. The HTTP routes and live-table events are not a versioned public API, but programs do drive them with a signed-in account. These are the changes such a program may notice; the changelog's entries explain each one for everyone else.

- *Live table: events.* A `token.move.end` refused because the sender may not move the token (`error` "You do not have permission to move this token" or "Spectators cannot move tokens") or may not act on its plane ("You cannot interact with spirit layer tokens") now always sends the sender, after the `error`, a `token.moved` with the token's stored position and `movedBy: null`, when the map fetch would give the sender that token. It used to be sent only when the same connection's `token.move.start` for the token had been accepted first; without one, the sender got only the `error`.
- *Live table: events.* One connection's `token.move.start` and `token.move.end` for the same token are now handled one after the other, in the order they arrive. The `token.move.start` a pick-up sends to others now always arrives before the `token.moved` of a drop sent right behind it, where the two could arrive the other way round, and a refused drop sent right behind its pick-up is now put back on the screens the pick-up reached. Events for different tokens do not wait for each other.
- *Live table: events.* `campaign.access.revoked` has a new `reason`, `not-member`, with the message "You are not a member of this campaign.". An `authenticate` naming a campaign the user is not a member of is answered with it; it was answered `error` "You are not a member of this campaign". One naming a campaign that does not exist is answered `campaign.access.revoked` with reason `campaign-deleted` and the message "This campaign does not exist. It may have been deleted."; it was answered `error` "Campaign not found". Either way `campaignId` is the campaign the `authenticate` named, the connection stays open, leaves every campaign room it was in (each of those campaigns gets `user.left` and `presence.state`) and is in no campaign, as after a removal. The other refusals of `authenticate` are still an `error`.
- *Live table: events.* A connection that asks to join a campaign within a minute of its user's removal or leave, or whose join finds the membership gone after it was first read, is sent `campaign.access.revoked` with the reason that removal or leave gave, `removed` ("You were removed from this campaign.") or `left` ("You left this campaign."). After the minute, or with no record of why, the reason is `not-member`. A join that found the membership gone on its second read always said `removed`. The minute is kept in the backend process's memory, so a restart forgets it.
- *Accounts and requests.* A user's `lastLoginAt` is now set when a sign-in completes: by `POST /api/auth/login` without two-factor authentication, `POST /api/auth/mfa/verify-login` with it, `POST /api/auth/register` when it signs the person in, and `POST /api/setup/init`. Registration and the setup wizard left it null, and `POST /api/auth/login` set it at the password step, including for a sign-in that then stopped at the code step or was refused with 403 `Account Pending Approval`. `POST /api/admin/users/:id/resend-invite` therefore answers 409 for an account that ran the setup wizard or registered and was signed in straight away (it answered 200), and 200 for an account whose only sign-in attempts were refused with 403 `Account Pending Approval` or stopped at the code step (it answered 409), since those no longer set `lastLoginAt`; and `POST /api/auth/reset-password` with an invitation link no longer restarts such an administrator's 7 days to set up two-factor authentication. `GET /api/auth/me` from a signed-in session sets a `lastLoginAt` that is still null, once, and the `user` it answers with carries the new value.
- *Accounts and requests.* The `RateLimit-*` headers on `POST /api/auth/mfa/verify-login` answers are now always the per-address limit's (5 wrong codes per 15 minutes from the address, `RateLimit-Policy: 5;w=900`), as on `POST /api/auth/login`. The per-account limit's replaced them, so `RateLimit-Remaining` counted the account's wrong codes from every address. The 429 `Too many MFA login attempts for this account, please try again later` keeps its `Retry-After`, and its `RateLimit-*` headers are now the address's.
- *Assets.* `DELETE /api/assets/:id` (with or without `force=true`) and `PATCH /api/assets/:id/scope` (a move out of the campaign) by a campaign asset's uploader who does not run the campaign now first read up to 100 of the campaign's other members' documents stored before 1.6.0 (a PDF among them, which names nothing) and not yet read for the assets they name. While any is still unread (more than 100 were waiting, another request is reading it, or its file could not be read), the delete answers 403 "Some older documents have not yet been checked for the pictures they show, so for now only the campaign's DM can delete this asset. Try again later." and the move 403 "Some older documents have not yet been checked for the pictures they show, so for now only the campaign's DM can move this asset out of the campaign. Try again later."; each request reads up to 100 more, newest first. A document whose file cannot be read is tried again by every request and keeps the refusal until it can be read; until then only the campaign's DM can delete or move the asset. A document read this way that shows the asset now gives the existing 403 "Others in the campaign use this asset, so only the campaign's DM can delete it" (the move: "Others in the campaign use this asset, so only the campaign's DM can move it out of the campaign"); before, until the document had been read, the delete answered 200 with `force=true` and 200 or 409 `ASSET_IN_USE` without it, and the move answered 200. The campaign's DM and admins are answered as before.
