# Security Policy

CozyVTT is a self-hosted virtual tabletop platform. We take security seriously and appreciate responsible disclosure from the community.

## Supported Versions

Since this software is still considered beta/WIP, support is only given for the latest version. Security patches are only available for the latest version and not back-ported to older versions.

Self-hosters are responsible for keeping their instances up to date.

## Reporting a Vulnerability

**Please do not open a public GitHub issue for security vulnerabilities.** Public disclosure before a fix is available puts every self-hosted instance at risk.

### Preferred — GitHub Private Vulnerability Reporting

Use the **"Report a vulnerability"** button on the [Security tab](https://github.com/CheekyChinchilla/CozyVTT/security) of this repository. This creates a private advisory that only repository maintainers can see.

### If you cannot use GitHub

If you have no GitHub account, or the button is not there, use the contact form linked under [Become a Collaborator](docs/CONTRIBUTING.md#-become-a-collaborator) in CONTRIBUTING.md to ask for another private way to send the details. Say only that you have a security report; put the details in nothing public and nothing you cannot take back.

### What to include

The version (`git describe --tags --always` in your CozyVTT folder), how it is installed, what you did, what happened and what you expected. Do not send your `.env`, a backup or a session cookie: describe the problem with a throwaway instance instead.

## What is in scope

- **In scope:** the code in this repository (the backend, the frontend and the live table) and the configuration it ships with (`docker-compose.yml`, `nginx/`, `.env.example`), run as the [deployment guide](docs/DEPLOYMENT.md) describes.
- **Out of scope:** a weakness that needs a change the guides tell you not to make; the security of your own server, firewall, proxy or tunnel; the software CozyVTT is built on, which belongs to its authors (but do tell us if CozyVTT's configuration makes a weakness in it worse); an action that needs an administrator's own account, since an administrator is trusted; and the output of a scanner with no demonstration that it matters.

## What to expect

CozyVTT is a one-person project run in spare time. A report is read and answered as soon as the maintainer can; there is no fixed response time. Please keep the details private until a fixed version is released and the reply says it is safe to share.

## Notes on the security design

Decisions a self-hoster or a reviewer may want to know about. The deployment guide's [Hardening Checklist](docs/DEPLOYMENT.md#hardening-checklist) says what to do; this says why the app behaves as it does.

- **First administrator.** Until the setup wizard has run, the instance refuses everything except the wizard, and the wizard asks for a one-time setup token that the backend prints in its log at start (or `SETUP_TOKEN` from `.env`). A stranger who reaches a fresh instance first therefore cannot make themselves its administrator. Finish setup before you share the address all the same.

- **Wrong passwords.** Counted twice: 5 per 15 minutes per visitor address, and 10 per hour per account from every address together, each lock noted in the admins' activity log. The password confirmed when changing the password or email or deleting the account has its own allowance of 10 per 15 minutes per account. Only a wrong answer ever counts, so correct sign-ins arriving together never lock anyone out, and an email with no account is counted and answered exactly as a wrong password, so the limits reveal nothing about who has an account. An unknown email is checked against a dummy password hash, so the time a sign-in takes reveals nothing either. A new password, however it is set, clears the account's count at once, so nobody can keep an account locked whose owner can reset the password.

- **What a session alone can do.** Anything that decides who can sign in from then on asks for the current password: changing it, changing the email address, turning two-factor authentication on or off, deleting the account. The admin reset routes ask for none, so they refuse the administrator's own account; an admin resetting someone else is written to the activity log. Forgot password issues at most one reset link every 5 minutes per account (an administrator's Send reset link and Resend invite are not under that cooldown), and reset links are limited per address as well.

- **Sessions.** A sign-in ends after an hour without a request (30 days with Remember me), and in any case 30 days after it was made (`REMEMBER_ME_MAX_AGE`), however active. An account keeps at most 20 live sign-ins. Changing or resetting a password, changing a role, turning two-factor authentication on or off and deleting an account end the account's other sign-ins, pending two-factor sign-ins included; a failure to do so fails the request. The session table holds the user id and role, when the sign-in was made, whether a password change is still required, and the two-factor pending state; never the password or a token.

- **Administrators and two-factor authentication.** An administrator account must have two-factor authentication on. One without it has 7 days to set it up, counted from the latest of the upgrade that introduced the rule, the account's creation, its promotion to administrator and a Reset MFA by another administrator; a banner says so on every page, and after the deadline the account can do nothing but set it up, change its password or sign out. Each of those moments is a line in the admins' activity log: the date the rule started on an instance is the first "Administrator accounts must use two-factor authentication" line, and promotions and resets are written there as they happen.

- **What a backup holds.** A backup is a full database dump, readable by whoever holds the file. Password hashes are Argon2id and backup codes are hashed; password reset and invitation links are stored as SHA-256 hashes of the token, so the dump holds no working link. **Two-factor (TOTP) secrets are stored as they are**, so a leaked backup lets a cracked password alone sign in to an account that has two-factor on. Encrypting them needs a key from the environment: a safe default with no new required setting would derive it from `SESSION_SECRET`, but rotating that secret would then break every authenticator. The decision for now is to leave them as they are and keep backups where only the administrator can read them; revisit when a key management story exists.

- **Who may name a visitor's address.** The per-address limits count the address the bundled nginx settles on. nginx believes the `X-Forwarded-For` and `X-Forwarded-Proto` headers only from its own loopback and from the addresses listed in `NGINX_TRUSTED_PROXIES` in `.env`, which is empty by default. Earlier versions believed them from every private address, which let a visitor whom Docker relays from its own gateway (one connecting over IPv6, or any visitor on Docker Desktop or rootless Docker) choose the address they were counted as. The cost of the narrower default is one line in `.env` for anyone with a tunnel or proxy in front of nginx. A visitor over IPv6 is counted by their /56 network, the block of addresses a provider usually gives one home, so moving between the addresses of that block buys no more requests or guesses.

- **The database role.** The backend connects to PostgreSQL as the role `docker-compose.yml` creates from `DATABASE_USER`, which the official PostgreSQL image makes a superuser. A superuser can run programs inside the database container and read its files, so SQL that reached the database by any route would run with that power. Restoring a backup is such a route: the restore checks a dump's statements, but that check is not a sandbox, which is why the deployment guide says to restore only backups you trust. A separate role that owns CozyVTT's tables without being a superuser would take that power away. That change is recorded for later: the restore replaces the whole schema as the superuser today, and existing installs would need an upgrade that creates the new role without a manual step.

- **What runs as root in the containers.** The backend, the two nginx containers and the database each start as root and switch to an unprivileged user (`appuser`, `nginx`, `postgres`) before they handle a request; nginx keeps a master process as root, which handles no request itself. All four run with `no-new-privileges`, and each drops every Linux capability Docker would give it except the few it uses as root: changing a file's owner and switching user in all four, listening on ports 80 and 443 in the two nginx containers, reading a folder or file that one account keeps private in the backend, the proxy and the database (the backups folder, PostgreSQL's data folder, a TLS key copied in with the deployment guide's steps), and, in the backend alone, setting the mode of a folder another account owns (the backups folder, once it is `appuser`'s). Root in a container can no longer make device files or send raw network packets, and can write a file another account owns only after changing that file's owner (or, in the backend, its mode). This is also why commands run inside the backend container take `-u appuser`. The frontend's, the proxy's and the backend's filesystems are read-only, apart from memory-backed folders for nginx's pid files and rendered settings, a volume for the proxy's uploads and downloads on their way through, and the backend's uploads, backups and logs folders and a `/tmp` volume for the working copy a backup or restore makes. A leftover working copy, from a backup or restore that was stopped part-way, is removed when the backend next starts.

- **Two-factor sign-ins.** A sign-in that has passed the password step but not the code is not signed in anywhere: the HTTP guards, the admin guards and the live-table handshake all read one definition. It expires 5 minutes after the password step, and it ends whenever the account's password is changed or reset or its sessions are ended for another reason.

- **Dependencies.** Every push to `dev` and `main`, and every pull request into them, checks the packages an instance runs against the published advisories (`npm audit`): a high or critical advisory in them fails the check. The developer tools (the test runners, the linter, the build tools) are checked too and reported without failing, since they never reach an instance. The backend's have none. In the app's, `npm audit` reports five, all high and all from one advisory in braces, a file-matching package that Tailwind CSS 3 brings with it to find the class names in the app's files while it is built. No release of braces fixes it; moving to Tailwind CSS 4, planned for 1.5.4, clears it. Dependabot proposes updates to the packages, to the Docker base images and to the CI actions each week, and each new major version of a package as a change of its own, apart from the few its settings name as waiting, each with the reason. The CI actions are pinned to commits, so a tag moved upstream cannot change what runs. Dependabot alerts are on, and from 1.5.3 its security updates too, which propose a fix as soon as an advisory is published for a package CozyVTT uses; both are repository settings.

- **Advisories in the libraries 1.5.1 and 1.5.2 shipped.** A published advisory is weighed against how CozyVTT uses the package. 1.5.1 shipped proxy-addr 2.0.7, the library Express uses to read a visitor's address from the proxies in front of it, which has a critical advisory in how it matches a list of trusted address ranges. The backend never reached that code: it trusts a count of one proxy, the bundled nginx, which Express checks by itself, and a test holds the setting to that count. Trusting a list of ranges instead would need proxy-addr 2.0.8 or later, which 1.5.2 installs. 1.5.1 also shipped sharp 0.35.4, the image library, which has a high-severity advisory in librsvg, the SVG renderer it bundles (GHSA-wq5f-xc86-pv6w), and any signed-in account could reach that one. 1.5.1 and earlier releases are affected; sharp 0.35.5, which 1.5.2 installs, fixes the advisory. 1.5.2 also closes the way an account could reach it: the backend now gives sharp only files whose content it has identified as PNG, JPEG, WebP or GIF, and switches off every reader in sharp but those four, the SVG renderer included. 1.5.2 and earlier releases shipped React Router 6, the library that moves between the app's pages, which has two moderate advisories fixed in 7.18.0: an address starting with a slash and a backslash, given to a link or a navigation, leads to another site (GHSA-wrjc-x8rr-h8h6), and error details carried in a page rendered on a server can make the browser call unexpected code (GHSA-337j-9hxr-rhxg). Neither could be reached. The one address the app takes from a link is the page to go back to after signing in, which it follows only when it is a path on this site with no backslash in it, and CozyVTT renders no page on a server. 1.5.3 installs React Router 8.4, which fixes both.

- **Where the packages come from.** Both lockfiles take every package from the npm registry with a hash of its contents, and the images install with `npm ci`, which refuses a package that does not match its hash; a backend test fails if a lockfile entry points anywhere else or has no hash. Each project's `package.json` names under `allowScripts` the packages that run a script while they install: the Prisma command-line tool and its engines package, which fetch the database engines, argon2, which checks for its prebuilt binary, and a few developer tools. A backend test fails when that list and the lockfile disagree, so a dependency that brings a new install script shows up in a reviewed change. Each project also turns on npm's `strict-allow-scripts` setting, so when a package with an install script is not on the list, the install fails before anything is installed, naming the package: in the image builds, in CI and on a developer's machine. Without the setting, npm 11, which builds the images, would run that script and print a warning. A released lockfile always matches its list, so this cannot stop a `docker compose up -d --build` of a release. The Prisma command-line tool is a runtime package, not a developer tool, because the backend applies database migrations with it every time it starts, so the image holds its whole tree. Since Prisma 7 that is about 125 packages more than before, among them React (for Prisma Studio, a database browser), a MySQL driver and an embedded PostgreSQL for Prisma's local development server, none of which an instance loads. It also brings the TypeScript compiler, about 23 MB, which Prisma names as an optional peer, so npm installs it in the image as well; only `prisma --version` loads it, to print its version number. The production check above covers them. Prisma 7.10.0 asks for two of them at versions with high advisories, the MySQL driver mysql2 3.15.3 and deepmerge-ts 7.1.5, which merges settings when the tool reads its configuration file, so CozyVTT installs mysql2 3.24.5 and deepmerge-ts 8.0.2 in their place.
